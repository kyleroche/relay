## Tasks and workers come from the board

relay's tasks and workers live on the team's Vercel Board (`docs/WORKERS.md`, "The board"), not in the database. The web app reads and writes them through `@relay/core`'s `board` namespace:

- `lib/board.ts`: the one handle. `siteBoard()` is the session (the deployment's own in db mode, an in-memory demo board from `lib/board-demo.ts` in mock mode); what the site does to a task for someone goes through core's desk (`lib/task-ops.ts`), which writes their words as a profile named for them. `siteWorkers()` is the fleet, cached 20 s. `siteReach()` is what the site may settle, asked of the board once per instance: Vercel's board gives a deployment no `manage`, so a hosted site settles the tasks opened through it (its deployment owns them) and `siteSettles(reach, task)` is false for one opened from a machine, where the card and the task page show `components/tasks/settle-elsewhere.tsx` (the `relay task` command) in place of the buttons.
- `lib/board-read.ts`: what pages read (`openTasks`, `recentTasks` for History newest first, `newestFinished` for the board's Done column, cached 20 s, `fleet`, `planMeters`, `waitingOnYou`). There is no task index in the database.
- `lib/task-ops.ts`: a thin adapter. Every write (open, approve, request changes, release, requeue, close) from the API routes and the server actions becomes a call on core's desk (`packages/core/src/board/desk.ts`), which the MCP server uses too. The desk holds the two voices (a caller's words go out as their profile, relay's own data as `relay-site`) and the two rules for a bot, which is a token rather than a signed-in person: it never approves a task it opened, and it never releases a task whose text it wrote any part of. A task the site opens has its brief in the thread before a worker can claim it. `lib/task-problem.ts` turns a refusal into a problem document.
- `lib/tasks.ts`: state copy and tones, the board's columns (`columnOf`), which decisions a state allows (`decisionsFor`), what a task in review asks for (`reviewKind`: a pull request to merge, a plan whose tasks an approval opens, a report to mark as read, outputs to accept), and the tasks an approved plan opened (`planOpened`). `lib/review.ts` is the words of an approval by kind and `lib/task-path.ts` the page path, both without imports, for client components.
- `lib/profile.ts`: a project's profile (`.relay/project.json`) as the site knows it: read from the repository's default branch through the site's GitHub client, parsed by core's `readProfile`, kept five minutes per repository and instance. The demo's profiles are `MOCK_PROFILES` in `lib/mock.ts`. No GitHub, or a read that fails, is no profile and one line of why; a repository without the file has the empty profile.
- Grants (`app/tasks/actions.ts`, the task page's Grants panel): `grantSetAction` grants a capability set of the profile and `approveCloudRunAction` a paid sandbox run up to a cap, both through core's `grantFor`, which lets only a signed-in person grant and ties the grant to the task's text. What is granted is always read with `board.grantsOf(thread, session.from)`: the authors the site believes, never a label or free text.
- `lib/board-watch.ts` and `app/api/board/[[...path]]/route.ts`: the watchers the board wakes the deployment for (`ledger` copies the queues' events into the feed, `relay-brief` posts the brief of a task opened elsewhere than the site, and `lead`, only where `RELAY_LEAD_URL` is set, wakes relay's lead), `taskBrief` (the brief the desk posts for a task the site opens), and the throttled sync page loads run where nothing wakes it.
- `lib/webhooks/board.ts`: what a GitHub delivery does on the board (an `agent:<lane>` label opens a task as the profile `github`, one per issue, on a lane somebody serves; a merge completes the task that waits on it). When it cannot, the route writes a `board.delivery_failed` row. `lib/webhooks/senders.ts` is who may open a task that way (`senderMayOpenTasks`: a login in `RELAY_ALLOWED_SENDERS`, and nobody when no allowlist is set); `lib/webhooks/github.ts` turns a delivery into its feed row (the lane of a pull request comes from a worker's `relay/<lane>-<8 hex>` branch, else from an `agent:<lane>` label).
- `lib/lead.ts`: `wakeLeadFor`, what the `lead` watcher runs. For a board event core's `leadWakeOf` names (a task that failed, was held at the gate or reached review) it posts to the lead's `/relay/wake`, signed with `RELAY_LEAD_WAKE_SECRET` (HMAC-SHA256 over the timestamp and the body; core's `wakeLead`). It sends no token, and never this deployment's own Vercel OIDC token, which is the site's credential on the board. Off unless `RELAY_LEAD_URL` is set; with the URL and no usable secret it sends nothing and says why once; a wake-up that fails is logged and dropped.

Tests run these on an in-memory board (`board.memoryBoard()`) and an in-memory PGlite; nothing needs a network.

## A paid sandbox run, only after a person approves the spend

The owner's rule: nothing spends money without the owner saying yes first, and waiting for one of their own machines is the default and needs no action. The decisions are pure and in core (`packages/core/src/cloud/`: `cloudOffer`, `estimateUsd`, `defaultCap`, `cloudRunPlan`, `cloudStart`); the site computes, asks, and turns a plan into SDK calls:

- `lib/cloud/config.ts`: what the deployment needs (`RELAY_GATEWAY_TOKEN`, `RELAY_GATEWAY_URL`, `RELAY_CLOUD_AFTER_MINUTES`, `RELAY_CLOUD_MAX_CAP_USD`; `.env.example`) and `cloudProblem()`, the one line when it is not set up. The version of relay a sandbox installs is `packages/cli/package.json`'s, read at build time.
- `lib/cloud/view.ts`: what a page shows for a queued task, computed from the board at render with nothing written: the offer (no worker on a person's subscriptions that is online or idle serves its lane, it has waited `RELAY_CLOUD_AFTER_MINUTES`, the project's profile does not say `cloud: never`), with an estimate (the median `cost_equiv` of the project's past `step.usage` rows of a run on the claude lane, "no history yet" under three) and a default cap; or the run a person already approved and where it stands. `components/tasks/cloud-offer.tsx` draws it on the card and the task page: "Run in cloud" opens a sheet with the cap to edit, "Keep waiting" folds the offer for that viewer (their browser's storage) and does nothing else. The sheet says, in words the server sends, what the yes does not cover: that the cap is relay's own count and code in the sandbox can spend past it (core's `CLOUD_CAP_NOTE`), that the path is experimental, and, when the branch rule below is missing, why Approve is off and what to turn on (`offer.blocked`).
- `lib/cloud/guard.ts`: the branch rule. `repoGuard(repo)` asks GitHub, as the site's App, whether the repository's default branch requires a pull request with an approval of the most recent push under a rule the App may not bypass (`GET /repos/{o}/{r}`, `/rules/branches/{branch}`, `/rulesets/{id}`, and classic protection when the App may read it); `branchGuard` is the decision, pure. `approveCloudRunAction` and the pool refuse a run without it, since the firewall cannot keep a GraphQL merge or a push off that branch. `test/cloud-guard.test.ts` decides over recorded response shapes; no test calls GitHub.
- `lib/cloud/pool.ts`: `runApproved()`, the only place a sandbox is started. It reads the queued tasks whose root carries the label `cloud=approved` (a hint core's `grantTask` sets with every grant of a paid run, the CLI's included; every five minutes it looks wider, for a grant whose label was taken off), and starts one sandbox for each that carries a trusted grant for its text as it stands, is not being started, whose project still allows it, and whose repository passes the branch rule (asked again at each start). `siteSecrets` gets a start's credentials: the board's policy held to the task's own queue (`cloudBoardCan(project)`), and a GitHub token minted with `CLOUD_GITHUB_PERMISSIONS` only. A start is marked in the thread as `relay-site` under a key made from the task, the grant and the try before the sandbox is made, so two instances start one. A start that did not come up is marked failed and tried again, three times at most; a start that may have run is never followed by another: the owner is asked again. Called from `approveCloudRunAction` (`after()`) and from `syncFeedAfter` in `lib/board-watch.ts`.
- `lib/cloud/launch.ts`: a plan to `@vercel/sandbox` calls (`Sandbox.create`, `runCommand`, `stop`). The three credentials (the board as this deployment under the worker's profile, from `board.sandboxPolicy`; an installation token of the site's GitHub App for the one repository; the gateway's key) are in the network policy's `transform` rules, which the sandbox's firewall applies; the environment inside holds placeholders, and `launch` refuses to start if a credential would be readable there, if GitHub's token may do more than the plan's `githubPermissions`, or if the board's policy is not the plan's queue and profile. The policy is deny-by-default: the board, the gateway's coding endpoint, GitHub, the npm registry and the hosts of the capability sets granted to the task. `githubRules` holds GitHub to the one repository: git's three endpoints on `github.com`, and `GET /`, `POST /graphql` and reads under `/repos/<repo>` on the API, with the REST merge, ref and branch-protection paths refused by name and everything else answered 403. Not readable is not unusable: the lane runs unsandboxed in there, so these rules are the list of what a fooled lane can do (`docs/SECURITY.md`, "What a paid run's lane can reach"), and `test/cloud-launch.test.ts` tests them as that.

No test creates a sandbox or calls the gateway: `test/cloud-launch.test.ts` and `test/cloud-pool.test.ts` pass their own `create`, credentials and launcher. Do the same in anything you add; a real start costs money.
