# AGENTS.md — relay

relay is an open-source harness that lets one person's coding-agent subscriptions (Claude, Codex, Grok) work as one system: GitHub issues are the task bus, workers (machines running `relay work`) on the user's own machines claim tasks from relay and execute them with the vendor CLIs under the machine's own login, a Postgres database holds shared memory and an append-only event feed, and a small web app shows it all. relay is its own scheduler; no GitHub Actions runner is required. Credentials never leave the machine they were created on.

## Layout

- `packages/core` — TypeScript library: `db/` (Postgres schema + migrations + typed queries; PGlite locally, Neon in production), `brief/` (the brief compiler and `relay.md` renderer), `memory/` (transcript capture: parse, gate, extract decisions with the Sonnet lane), `onboard/` (official-vendor-docs ingestion gate), `lanes/` (headless adapters for `claude -p`, `fx`, `codex exec`, `grok -p`; `sandbox.ts` builds the `--settings` document that puts the Claude lane's Bash in Claude Code's OS sandbox on every code run, the tool allowlist in `work/job.ts` being the second layer; `nodes.ts` is the Griptape Nodes lane: it runs `packages/cli/python/run_workflow.py` under the engine's own Python (found through the `griptape-nodes` launcher's shebang, `RELAY_NODES_PYTHON` or `uv tool run`), maps the node types it ran to model ids (`NODE_MODELS`) and turns the outputs into one `step.usage` per output model on lane `video` | `image` | `audio`), `ledger/` (step.usage writer, the token price table and `MEDIA_PRICES` for per-output media models; an unpriced model is recorded with `cost_unknown: true`), `assets/` (Blob or local store, versions, review), `rules/` (owned-section installer for `AGENTS.md`/`CLAUDE.md`), `hooks/` (per-CLI hook installers, including Claude Code's `statusLine`, installers and the brief cache), `meters.ts` (plan-meter readings: the file relay's status line writes under `~/.harness/meters`, what the worker heartbeat sends, what the server accepts), `state/` (project registration and file digests), `tasks/` (`openTask`: a GitHub issue with a lane label, state derived from the feed and cached on the task row after every write that can change it (`db/task-state.ts`: `refreshTaskState`, `boardTasks`, the one-query read the board uses; `station.ts`: the station derivation, pure, imported by the web through `@relay/core/tasks/station.ts`); `approveTask` / `requestChanges` in `review.ts`: the review step that merges or sends back; `requeueTask` in `requeue.ts`: back to the queue from any state but done, optionally on another lane, moving the `agent:*` label, releasing a live claim and writing `task.requeued`; `gate.ts`: the injection gate, a deterministic pre-check plus one Sonnet call with no tools that grades the issue text before a worker runs it, `task.held` / `held` until `releaseTask` writes `task.released`; `manifest.ts`: the nodes lane's ```relay-nodes block, parsed from the issue body (JSON or a small YAML subset, no library) into the workflow path, the flow inputs and the end nodes to keep), `github/` (`client.ts`: issues, labels and comments over the GitHub App, `GITHUB_TOKEN` or `gh`; `app.ts`: installation tokens from `GITHUB_APP_ID` + `GITHUB_APP_PRIVATE_KEY` via jose, cached per installation), `oauth/` (the OAuth 2.1 authorization server, framework-free: PKCE codes, refresh rotation, RFC 8628 device codes, RFC 7591 registration, revocation, the `urn:relay:invite` grant; `db/oauth.ts` holds its queries, `db/settings.ts` the sealed settings), `webhooks/` (signed outbound deliveries with retries), `client/` (`RelayClient`: the command surface over the local database or a hosted site, chosen by `openHarness()`, including `githubStatus(slug)` (`GET /api/v1/projects/{slug}/github` on a site; no App and the site's `/setup/github` as install link locally); `device.ts` is the CLI side of the device flow, invites and refresh), `work/` (the scheduler and the worker: `server.ts` the protocol over the `workers`/`claims` tables, `api.ts` the local and HTTP `WorkApi`, `job.ts` one claimed task to a PR (or, on the `nodes` lane, one workflow run to assets on the issue: `runNodesStage`, with `WorkApi.uploadAsset` / `assetsForIssue` and `release`'s `extra_usage` rows), `worker.ts` the claim loop, which reads the doorbell (`queue_state.version` plus a queued count, `db/queue.ts`) on a tick that doubles from 15 s to 5 min while idle and claims only when the version moved, `service.ts` the LaunchAgent/systemd files; `db/workers.ts` holds `claimNext`, the leases and `doorbell`).
- `packages/cli` — the `relay` command. `src/commands/` holds one file per command group (`setup`, `link`, `brief`, `recall`, `decide`, `prefer`, `capture`, `memory`, `assets`, `token`, `invite`, `task`, `webhook`, `work`, `lane`; `probes.ts` is the login and sandbox detection `doctor` and `work` share, including `nodesCheck`, the `nodes` doctor line that makes a machine with the Griptape Nodes engine serve the `nodes` lane), `python/run_workflow.py` is the Griptape Nodes shim (dependency-free beyond the engine; `--workflow`, `--inputs <json file>`, `--out <dir>`, `--outputs`; one JSON document on stdout), `hooks/*.mjs` are the dependency-free scripts the CLIs' hooks point at (`statusline.mjs` is Claude Code's status-line command: it saves the plan meters Claude Code reports to `~/.harness/meters/claude.json`, then runs the status line that was there before), at, `templates/` the Actions caller workflows `relay link --workflows` installs. `relay onboard <model>` ingests vendor guidance; `relay feed`, `relay usage`, `relay doctor`; `relay token create` mints scoped bearer tokens for the web app (hash stored, shown once); `relay task` opens and reads tasks; `relay webhook` manages outbound webhooks; `relay work` makes the machine a worker (`--once`, `--install`/`--uninstall` for the LaunchAgent or systemd unit, `work status`, `work forget <name>` for a retired row; `--no-sandbox` turns the Claude lane's OS sandbox off, logged and advertised as the label `sandbox:off`; `--isolation container` runs the whole worker in the `relay-work` container made with Apple's `container` CLI from `container/Dockerfile`, shipped as `dist/container/`: `--install` builds the image, creates the container on a named volume with no host mounts, runs `relay setup --site` inside and installs a service that runs `container start --attach`; `work container shell|status|stop|start|rm|logs` wrap it; `work container update` rebuilds the image and recreates the container on the same volume, skipping `relay setup --site` when the volume holds a token; `work container login [claude|gh|codex|grok|all]` makes the logins inside from the Mac (claude and gh as TTY passthroughs; for codex and grok fx runs inside with `FX_NO_OPEN_BROWSER=1`, its authorize URL is opened in the Mac's browser and the redirect caught by a listener on the Mac at the port fx registered, the code then pasted to fx or, for codex, replayed to its listener inside; the pure parsing is `packages/core/src/work/login.ts`); inside, the worker registers as `<host>-container` with `isolation:container` and `sandbox:on` or `sandbox:container`; `docs/WORKERS.md` "Isolation"); `relay lane settings` prints the sandbox `--settings` JSON for scripts such as `run-lane.sh`; `relay lane nodes --workflow <file> --inputs '<json>'` runs one Griptape Nodes workflow through the nodes adapter by hand (outputs in `--out`, usage rows in the local ledger). `relay setup --site <url>` puts the CLI in site mode through the device flow (it prints a code approved at `<site>/activate`; `--invite <code>` redeems an invite instead, `--token <t>` pastes one): commands and hooks call the hosted site's `/api/v1` and `/mcp` instead of a local database and the token renews itself (`docs/MEMORY.md`, "Site mode"). `relay invite create` mints one-time codes; `relay doctor` shows how the machine authenticates. Published to npm as `@kyleroche/relay`: `tsup.config.ts` bundles `src/main.ts` and the MCP stdio entry with `@relay/core` and `@relay/mcp` into `dist/relay.js` and `dist/relay-mcp.js` (runtime dependencies stay external and are listed in `package.json`, `sharp` optional), and `scripts/postbuild.mjs` copies `hooks/*.mjs`, `python/*.py`, the SQL migrations and `container/` beside them. `runtimePaths()` in `packages/core/src/runtime.ts` tells the hook installers, the migration loader and loader, the template copier and the container installer where relay's files are in either layout (checkout or installed package); path code does not count `..` from `import.meta.url` on its own, because the bundle has one `import.meta.url` for every module.
- `packages/daemon` — a Hono HTTP shell from the first scaffold, not used by anything yet; kept as the seat of a future long-running local service.
- `packages/mcp` — the relay MCP server `@relay/mcp`: `bin/relay-mcp.mjs` (stdio for the CLIs from a checkout; the published package ships it bundled as `dist/relay-mcp.js`; in site mode it opens no database and `src/bridge.ts` forwards every message to `<site>/mcp` with the machine's token, renewing it on expiry or a 401, so the tools and answers are the site's), `createMcpHandler` (Streamable HTTP for the web app), one tool set for both: public read tools (`relay_get_*`), memory tools (`relay_recall`, `relay_brief`, `relay_guidance`, `relay_feed`, `relay_project`, `relay_decide`, `relay_prefer`), asset tools (`relay_asset_*`), task tools (`relay_task_create`, `relay_task_get`, `relay_task_list`, the review step `relay_task_approve` / `relay_task_request_changes` under `tasks:write`: a bot never approves a PR its own lane produced, `relay_task_requeue`: back to the queue from any state but done, optionally on another lane, and `relay_task_release` under `tokens:write`: lift the injection gate's hold, never on a task the bot opened), `relay_event_log` (external bots' own `external.*` events, actor always `bot:<token name>`), `relay_webhook_subscribe` / `relay_webhook_unsubscribe`, the public `relay_whoami`, and the `tokens:write` access tools (`relay_access_list`, `relay_access_approve`, `relay_invite_create`, `relay_invite_revoke`: a chief-of-staff bot approves other agents' device codes and mints invites, for scopes it holds itself and never `tokens:write`), gated by the scopes a token carries (`TOOL_SCOPES` in `src/server.ts`).
- `apps/web` — Next.js app: the board (`/` for a signed-in viewer: one column per task state, the approve / request-changes / release / requeue actions on the cards, re-rendered every 20 s; the public landing for an anonymous one), the event feed (`/feed`, the board's second tab), task pages (`/tasks/<owner>/<repo>/<n>` with the preview link, the same actions and the run history; `/tasks` itself redirects to the board), projects, usage meters, workers, asset library with review (`/assets`), the Access page (`/access`, with `/tokens` redirecting to it: device requests with Approve/Deny, every token and how it was issued, invites, registered clients, the by-hand mint folded away), the OAuth 2.1 authorization server (`/.well-known/oauth-authorization-server`, `/oauth/register|authorize|token|device|revoke`, the consent page, `/activate` for device codes; `lib/oauth.ts` wires `@relay/core`'s server to the site), the GitHub App setup (`/setup/github` with the one-click manifest flow; `lib/github-app.ts` resolves the app from the environment or the sealed settings), info and docs pages, webhook ingest (GitHub org or App deliveries, Vercel), the public read API, the asset API, tasks, external events, tokens, invites, access approvals (`/api/v1/access`), `whoami`, the GitHub status of a project (`/api/v1/projects/{slug}/github`), outbound webhooks, project uploads and the worker protocol (`/api/v1/workers`, `/api/v1/work/*`, `docs/WORKERS.md`) under `/api/v1`, server-side cloud-lane dispatch (`lib/cloud-dispatch.ts`, in `after()` on task creation), the MCP server at `/mcp`, the retention crons (`/api/cron/assets-expire`, `/api/cron/access-expire`), and the agent-readiness files (`/.well-known/*`, `/openapi.json`, `/llms.txt`). Outbound webhooks fan out from `lib/dispatch.ts` with `after()` wherever a feed row is written. Data goes through `apps/web/lib/data.ts`: `RELAY_DATA=db` or any `DATABASE_URL` selects `lib/data-db.ts` over `@relay/core` (PGlite when `DATABASE_URL` is unset, one handle per instance in `lib/db.ts`); otherwise `lib/data-mock.ts` serves `lib/mock.ts`. Bearer tokens are checked in `lib/auth.ts` (`tokens` table with expiry, then `RELAY_API_TOKENS`, then `RELAY_MEMORY_TOKEN`); every 401 names the authorization server through `resource_metadata`. `DESIGN.md` there holds the UX brief and tokens.
- `skills/relay/SKILL.md` — the agent skill for installing relay, served at `/.well-known/agent-skills/index.json`.
- `.github/workflows` — reusable runner workflows that repos call with a thin caller.
- `docs/` — `ARCHITECTURE.md` is the source of truth for design; `AGENT-READINESS.md` is the contract for the hosted site; `VERSIONING.md` is the API deprecation policy; `INTEGRATIONS.md` is the connect-in-one-step guide (OAuth with consent, device flow, invite codes, the GitHub App, tools, webhook contract, Grok Bot walkthrough); `SECURITY.md` ("Access for agents") has token lifetimes, rotation and revocation; `HOSTING.md` has the GitHub App setup; `research/` holds dated surveys.

## Commands

```bash
pnpm install          # Node 24+ required (.node-version); bin/relay finds one itself
pnpm -r typecheck
pnpm -r test          # vitest; DB tests run on PGlite, no server needed
pnpm relay --help
pnpm relay setup      # plan hooks + MCP server for the CLIs on this machine (+ Claude Code's plan-meter status line; --no-statusline skips it); --yes writes
pnpm relay link       # in a repo (bin/relay link from elsewhere): digests, summary, relay.md, owned sections, labels, GitHub App check (site mode); --workflows adds the Actions callers; idempotent
pnpm relay brief 42   # the memory envelope a lane would get for issue 42
pnpm relay work --once                            # claim and run queued tasks for the lanes this machine is logged in to, then exit
pnpm relay work --install                         # plan the LaunchAgent / systemd user unit that keeps `relay work` running; --yes writes and starts it
pnpm relay work --isolation container --install   # the container tier (macOS, Apple's `container`): image, relay-work container on a volume, relay setup --site inside, service; --yes does it
pnpm relay work container login all               # the vendor logins inside relay-work, from the Mac: claude and gh in this terminal, codex and grok through this Mac's browser (or one: login grok; --force redoes one; --no-open prints the URL)
pnpm relay work container status                  # relay-work running?, the image it runs, relay doctor inside, the lanes it serves (also shell|stop|start|rm|logs)
pnpm relay work container update --yes            # after git pull or a package upgrade: rebuild the image, recreate relay-work on the same volume (site token and logins kept, no new device flow)
pnpm relay work status                            # the service, the site's workers (`retired` after 7 days offline), the log tail
pnpm relay work forget <name>                     # remove a retired worker's row (renamed or decommissioned machine); its runs stay attributed, it re-registers if it runs relay work again
pnpm --filter @kyleroche/relay build              # the npm package: packages/cli/dist (relay.js, relay-mcp.js, hooks/, migrations/)
scripts/check-package.sh                          # build, pack, install the tarball into an empty directory, run relay and relay-mcp from there (CI runs it)
pnpm --filter @relay/web dev                      # mock data
RELAY_DATA=db pnpm --filter @relay/web dev        # the CLI's PGlite file (stop the CLI first; PGlite is single-process)
pnpm --filter @relay/web build && pnpm --filter @relay/web typecheck
pnpm relay token create --name ci --scopes feed:read,assets:write   # bearer token for /api/v1 and /mcp, shown once
pnpm relay setup --site https://relay.kyro.house                    # site mode via the device flow: approve the printed code at /activate; --invite <code> or --token <t> instead; --no-site reverts
pnpm relay invite create --for concierge --scopes tasks:read,tasks:write,events:write --expires 24h --uses 1   # one-time code; redeemed with --invite or grant urn:relay:invite
pnpm relay task create --title "Add dark mode" --lane codex --priority high   # open a task (GitHub issue + label); relay task get <owner/repo#n>, relay task ls --state review|held, relay task release <id> (lift the injection gate's hold; RELAY_GATE=off on a worker skips its model call)
pnpm relay task create --title "Cutscene 3" --lane nodes --body-file shot.md  # a production task: the body's ```relay-nodes block names the workflow .py in the repo and its inputs; a worker with Griptape Nodes runs it and uploads the outputs as assets on the issue (docs/WORKERS.md, "The nodes lane")
pnpm relay lane nodes --workflow workflows/cutscene.py --inputs '{"Start Flow": {"prompt": "..."}}' --out out/   # the same engine run by hand, outputs in out/, usage rows in the local ledger
pnpm relay task approve <owner/repo#n>                                        # squash-merge the PR of a task in review; relay task changes <id> --note "…" sends it back to the queue
pnpm relay webhook add --url https://bot.example/relay --events pr.merged,run.failed --bearer <key>   # outbound webhook; secret shown once; relay webhook test <id>
RELAY_PUBLIC_URL=https://relay.kyro.house pnpm --filter @relay/web check:agentic   # is-agentic score gate, after deploy
```

Memory commands (`docs/MEMORY.md`): `relay brief`, `relay recall`, `relay decide`, `relay prefer`, `relay capture`, `relay memory history`. `relay setup` records the hooks and the MCP server as absolute paths: the installed package's `dist/` files when it ran from `npx @kyleroche/relay`, the checkout's `packages/cli/hooks` scripts (which call the CLI through the repo's own `tsx`) when it ran from a clone, so a clone must stay where `relay setup` ran (re-run it after moving).

## Conventions

- TypeScript strict, ESM, `.ts` imports with extensions. No default exports except Next.js pages/routes.
- Plain SQL migrations in `packages/core/src/db/migrations/NNN_*.sql`; never edit a shipped migration.
- Every model call goes through a lane adapter and writes a `step.usage` event. Nothing calls a model directly.
- Official vendor sources only for model guidance (`onboard/registry.ts` allowlists domains). Do not add community prompt guides.
- Secrets live in environment variables, never in files or examples. `.env.example` lists names only.
- Keep `AGENTS.md`, `llms.txt`, and `README.md` accurate when you change commands or layout; CI checks that README commands exist.
- Commit messages: imperative, one topic each. Do not commit generated output, databases, or anything under `.harness/`.

## Installing relay for a user (agent instructions)

If a user asks you to set up relay, do these steps and stop at anything that needs their browser. Their request is the consent for the writes below: when they asked you to set relay up on this machine, make it a worker, or link a repo, run the `--yes` forms without asking again; print the plan and ask only when nobody asked for that step.

relay is on npm as `@kyleroche/relay`; `npx @kyleroche/relay <command>` runs it with no checkout, and `npm install -g @kyleroche/relay` installs the `relay` command (if the shell then cannot find it, npm's global bin directory is not on PATH; `relay doctor`'s `path` line prints the exact fix). It needs Node 24 or newer: check `node -v` first and have the user install 24 (their version manager, or `brew install node@24`) if it is older.

When the user says "set up relay from `<site>` on this machine" (a hosted relay exists), the sequence is: `npx @kyleroche/relay setup --site <site>` (device flow in the user's browser, or `--invite <code>`), `npx @kyleroche/relay doctor`, `npx @kyleroche/relay work --install --yes`, then report the lanes the worker now serves. In full:

1. `npx @kyleroche/relay setup --site <site>` — joins the hosted relay: the site URL goes to `~/.harness/config.json`, a scoped token to `~/.harness/credentials.json` (0600). The device flow needs the user's browser; `--invite <code>` skips it. Without a hosted site skip this step: everything below uses the embedded database under `~/.harness` and `relay work` schedules that machine's own tasks.
2. `npx @kyleroche/relay doctor` — reports which CLIs are installed and logged in (`claude`, `codex` or `fx`, `grok`, `gh`), Node version, the site check, database reachability, and a `lanes` line: the lanes `relay work` would serve from these logins. Tell the user what is missing; logins are theirs to do (`gh auth login` and `gh auth setup-git` are needed for every lane, since the worker pushes as the gh account).
3. `npx @kyleroche/relay work --install` — prints the service file (a LaunchAgent on macOS, a systemd user unit on Linux) that keeps `relay work` running, and writes nothing; `--install --yes` writes and starts it (the user's request to make this machine a worker is the consent). `npx @kyleroche/relay work status` shows the service, the site's workers and the log tail; report the lanes this worker serves. `--lanes claude,codex` forces a subset, `--labels gpu` advertises capabilities, `relay work --once` drains the queue in the foreground. `docs/WORKERS.md` has the protocol and the troubleshooting. On a Mac with Apple's `container` CLI installed (`doctor` has a `container` line), prefer the container tier when the user asks for isolation or the Mac is their daily machine: `npx @kyleroche/relay work --isolation container --install --yes` builds the image, creates the `relay-work` container, runs the device flow inside (the code prints to the terminal; stop for the user's browser) and installs the service; then the logins happen inside and are the user's to do, with one command from the Mac: `npx @kyleroche/relay work container login all` (claude and gh run in the terminal: `/login` with a pasted code, a device code; codex and grok open the Mac's browser and relay catches the redirect; logins already in the volume are skipped). Run it in the user's terminal, since it needs their browser and keyboard; stop and tell them when it waits. The by-hand fallback it prints on a failure: `relay work container shell`, then `claude` (`/login`), `gh auth login && gh auth setup-git`, `fx login codex`, `FX_NO_OPEN_BROWSER=1 fx login grok` (paste only the `code` value from the unreachable callback page). `relay work container status` shows the lanes the container worker serves. Nothing from the Mac's home is mounted into it. After `git pull` or a package upgrade, `npx @kyleroche/relay work container update --yes` rebuilds the image and recreates the container; the volume's site token and logins are kept, so no new device flow.
4. `npx @kyleroche/relay setup` — prints every file it would touch in `~/.claude`, `~/.codex`, `~/.grok` (hooks, the memory MCP server, and Claude Code's `statusLine`: relay's status-line script saves the 5-hour and weekly plan usage Claude Code reports to `~/.harness/meters`, which is where the web app's header meters come from; a status line the user already has is kept and run by relay's; `--no-statusline` skips it) and writes nothing; run `npx @kyleroche/relay setup --yes` when the user asked for relay on this machine; ask first only if they did not. The hooks record the installed package's own files and the Node that ran `setup`. The meters file appears after the user's first interactive `claude` session; `relay doctor` shows it.
5. In each repo they want managed: `cd <repo> && npx @kyleroche/relay link`. This is the only per-repo step and runs the whole pipeline: registers the project and hashes its files, digests the changed files and writes the project summary (Sonnet lane, needs the `claude` login; `--no-digest` skips it, `--max-files` caps it at 400 by default), writes `relay.md` from that summary, adds the owned section to `AGENTS.md`/`CLAUDE.md`, the GitHub labels (`gh`), and the optional caller workflows (`--no-workflows` skips them; a worker needs none). It prints every stage and ends with one cost line. In site mode its last stage, `events`, checks that the site's GitHub App is installed on the repo and prints the install link when it is not; give that link to the user (one install covers every repo they pick). `--no-events` skips it. Re-running is safe and makes no model calls unless files changed; `--refresh` rewrites the summary. Do not run `relay project digest` or `relay project summarize` by hand.
6. Optional, for a model the user will prompt (image/video models): `npx @kyleroche/relay onboard <provider/model>`.
7. Optional, advanced: `docs/RUNNERS.md` covers self-hosted GitHub Actions runners for people who already operate them, and the cloud lanes' vendor setup.

If you are an agent that wants to call the hosted site yourself, request access the same way, without a human handing you a token: `POST <site>/oauth/device` (`client_name`, `scope`), show the user the `user_code` to approve at `<site>/activate`, poll `POST <site>/oauth/token` with `grant_type=urn:ietf:params:oauth:grant-type:device_code`, then call `/mcp` or `/api/v1` with the bearer; `docs/INTEGRATIONS.md` has the sequence and the invite and consent alternatives.

From a checkout instead (contributors, or a machine that should track `main`): `git clone <repo> && cd relay && pnpm install`, then `pnpm relay doctor`, `pnpm relay setup` and `pnpm relay work --install` (through `pnpm`, so the hooks and the service record the pinned Node 24) and `<relay checkout>/bin/relay link` in each repo. Everything else is the same.

### A clean machine, what the first install hits

Lessons from real installs; `relay doctor` prints the fix for each, give it to the user verbatim:

- **Node 24 without Homebrew**: the installer from nodejs.org, or a version manager; `relay` refuses older Node. Check `node -v` before anything.
- **`relay` not found after `npm install -g`**: npm's global bin directory is not on the shell's PATH (a prefix such as `~/.local/node`); `relay doctor`'s `path` line prints the `echo 'export PATH=…' >> ~/.zshrc` line. `npx @kyleroche/relay <command>` works meanwhile.
- **`gh` missing and no Homebrew**: the macOS pkg from https://github.com/cli/cli/releases/latest, then `gh auth login && gh auth setup-git`. No lane can push without it.
- **Codex and Grok lanes** need `fx` (tarball from https://releases.fx.sh) or the vendor CLIs, each logged in; a machine with only the Claude login is a claude-only worker, which is fine.
- **`launchctl bootstrap gui/<uid>` fails with "Input/output error"** when the user has no desktop session (SSH onto a Mac nobody is logged into). relay falls back to the `user/<uid>` domain and says so; for a worker that must survive logouts, log in once on the screen (or enable automatic login) and re-run `relay work --install --yes`.
- **The container tier** (`--isolation container`) needs Apple's `container` tool installed and `container system start`; without it, use host mode (`relay work --install --yes`), which still runs the Claude lane in Claude Code's own sandbox.
- **Stop at anything that needs the user's browser or password**: logins, the device code on `/activate`, installers.

Never move or copy a login, token, or `auth.json` between machines. Never run with permission checks disabled on a machine that holds the user's logins; `relay work` never passes a bypass flag.
