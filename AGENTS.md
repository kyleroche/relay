# AGENTS.md — relay

relay is an open-source harness that lets one person's coding-agent subscriptions (Claude, Codex, Grok) work as one system: the team's Vercel Board is the task bus (a task is a thread in its project's queue, `work/<project>`), workers (machines running `relay work`) on the user's own machines claim tasks from the board with the machine's own `vercel login` and execute them with the vendor CLIs under the machine's own login, pull requests land on GitHub, a Postgres database holds shared memory and an append-only event feed, and a small web app shows it all. No GitHub Actions runner is required. Credentials never leave the machine they were created on.

The CLI, the worker, the web app, its `/api/v1` task routes and the MCP `relay_task_*` tools all read and write tasks on the board through the same functions (`packages/core/src/board/tasks.ts`). The database holds memory, the feed, assets and access; it has no task or worker tables in use.

## Layout

- `packages/core` — TypeScript library: `db/` (Postgres schema + migrations + typed queries for memory, the feed, projects, assets, tokens, OAuth and settings; PGlite locally, Neon in production; the tables of the earlier task model stay in the schema, unused), `board/` (relay on a Vercel Board, exported from `@relay/core` as `board`: `client.ts` the handle, with no relay credential behind it, since `@vercel/board` finds the caller's own (the machine's `vercel login`, `BOARD_TOKEN`, or the board at `BOARD_URL`), and `connectBoard`, which adds who the caller is and the owners it takes tasks from (`from`); `mapping.ts` the vocabulary, pure: the channels `work/<project>` (a project's queue) and `relay/workers`, the labels, which only steer (`lane` and `model` on a task, `cloud=approved` on a task as a hint that a paid run was granted, `relay=<kind>` on relay's own replies), the hold kinds (`awaiting_review` with the pull request's URL as its reason, or the word `report`; `gate`; `awaiting_eval`; `awaiting_plan`, whose reason names the reply that carries the plan and its sha256; `relayState` shows a plan hold as `review` too), `relayState` (the board's task state plus the hold's kind as one word: waiting, queued, running, review, held, blocked, done, failed, closed), `branchFor` (`relay/<lane>-<8 hex of the task ID's hash>`) and `isBranchOf`; `schemas.ts` the registered blocks, which carry what relay acts on: `relay-task@1` in a task's own text (repo, base, issue; step, evaluates, branch on a step's task), `relay-run@1` (a run's outcome, branch, pull request, eval task), `relay-eval@1` (an eval's verdict), `relay-release@1` (a gate release, by the digest of the text), `relay-grant@1` (one grant for one task, by the same digest: a capability set of the project's profile, or a cap in US dollars on a paid sandbox run), `relay-usage@1`, `relay-worker@1`, `relay-asset@1`, with `ensureSchemas`, `isTrustedActor` and `trustedBlocks` (data in a reply counts only from a trusted principal itself or from relay's own `relay-…` profiles of it: a worker's `relay-<worker>-<lane>`, a site's `relay-site` and `relay-brief`; a profile a site writes for a person or a bot never starts that way, so a caller's words are never data), `isDecidingActor` (a grant or a gate release is believed from fewer authors: a trusted principal itself or the site's own `relay-site` profile of one, never a worker's profile, which `trustedBlocks` applies with `deciding`) and `prose` (the second layer: a fence in someone else's words that the board would read as a block is posted as a plain one); `tasks.ts` the task commands over the caller's own handle: `openTask` (made out of every worker's reach, pre-checked, then released or held), `openTaskHeldBack`, `getTask` (a thread outside a project's queue is no task; with `trusted`, only relay's own usage rows), `listTasks` (one state or several, oldest first; `open` is everything not done or closed, failed included), `recentTasks` (newest first by latest activity, for the site's Done column and History), `asOwner` (the calls the board keeps for a task's owner, lifting a hold, reopening and cancelling, go out as the caller's principal itself, since the board holds a profile to what that profile made and relay's profiles only say whose words a message carries), `approveTask` (checks that the caller can settle the task, as its owner or a manager of its queue, before anything merges, merges the pull request the hold names only if its head is a branch relay pushed for the task, or accepts a nodes task's outputs, or settles a report as read, or for a plan hold opens the plan's tasks as the approver (`plan.json` read from the reply the hold names and checked against its sha256, each task under the idempotency key `plan:<task id>:<key>`), then completes; a task whose own pull request is already merged is finished from any open state), `requestChanges`, `requeueTask`, `closeTask` (cancels, calls off a step's task that looked at it, sends the work a closed step's task was looking at to review, closes its own open pull requests and deletes their branches), `releaseTask` (a `relay-release@1` block, then the unblock), `grantTask` (a `relay-grant@1` block in a log reply: exactly one of a set or a cap above 0 and at most 1000 US dollars, refused on a done or closed task) which also sets the `cloud=approved` label for a cap, with `grantsOf` (the grants from who may decide whose digest matches the task's title and body as they stand, so a grant given before an edit counts for nothing), and `takeHeld`, which takes the `lane` label off before lifting a hold so no worker gets in between; `workers.ts` one message per worker machine in `relay/workers`, its text a `relay-worker@1` block edited in place and its labels `worker`, `status`, `running`, `seen`: `registerWorker`, `listWorkers`, `servedLanes` (the lanes of workers that are online or idle), `forgetWorker` (hides it with a `forgotten` label) and the online / idle / offline / retired thresholds, and `openServedTask`, the open every surface that takes a lane from a person or a bot goes through; `plan.ts` the plan a planning task delivers, pure: a fenced `relay-plan` JSON block at the end of the lane's answer (`parsePlan`), validated by `planProblem` (at most 20 tasks, each with a key, a title, a body of 40 to 20,000 characters and a lane; `needs` name keys of the same plan, with no cycle), posted as the attachment `plan.json`; `site.ts` what a hosted relay does on the board besides (`docs/ARCHITECTURE.md`, "The site and the board"): `actorProfile` (the site writes for each person or bot as a profile named for them, `human-…` or `bot-…`), `SITE_PROFILE` / `BRIEF_PROFILE` / `INTAKE_PROFILE` (`relay-site` for the site's own data, `relay-brief` for its briefs, `github` for GitHub intake), `syncLedger` / `ledgerRows` (board events become feed rows, from a cursor kept in the settings table; `docs/STEPS.md`; `profile.ts`: the rest of `.relay/project.json`, the project profile (`readProfile`: `setup` and `verify` commands, `tools`, `skills`, the capability `sets` (environment variable names and hosts, never values), `vercel` (the project granted values are read from) and `cloud` (`ask` | `never`); ## Conventions

- TypeScript strict, ESM, `.ts` imports with extensions. No default exports except Next.js pages/routes.
- Plain SQL migrations in `packages/core/src/db/migrations/NNN_*.sql`; never edit a shipped migration.
- Every model call relay's packages make goes through a lane adapter and writes a `step.usage` event. Nothing calls a model directly. The one exception is the lead (`apps/lead`): its model calls are its framework's, through Vercel AI Gateway, and it logs each turn as an `external.lead.usage` event.
- Official vendor sources only for model guidance (`onboard/registry.ts` allowlists domains). Do not add community prompt guides.
- Secrets live in environment variables, never in files or examples. `.env.example` lists names only.
- Keep `AGENTS.md`, `llms.txt`, and `README.md` accurate when you change commands or layout; CI checks that README commands exist.
- Commit messages: imperative, one topic each. Do not commit generated output, databases, or anything under `.harness/`.

## Installing relay for a user (agent instructions)

If a user asks you to set up relay, do these steps and stop at anything that needs their browser. Their request is the consent for the writes below: when they asked you to set relay up on this machine, make it a worker, or link a repo, run the `--yes` forms without asking again; print the plan and ask only when nobody asked for that step.

relay is on npm as `@kyleroche/relay`; `npx @kyleroche/relay <command>` runs it with no checkout, and `npm install -g @kyleroche/relay` installs the `relay` command (if the shell then cannot find it, npm's global bin directory is not on PATH; `relay doctor`'s `path` line prints the exact fix). It needs Node 24 or newer: check `node -v` first and have the user install 24 (their version manager, or `brew install node@24`) if it is older.

When the user says "set up relay from `<site>` on this machine" (a hosted relay exists), the sequence is: `npx @kyleroche/relay setup --site <site>` (device flow in the user's browser, or `--invite <code>`), `vercel login` (the user's browser) and `npx @kyleroche/relay setup --board`, `npx @kyleroche/relay doctor`, `npx @kyleroche/relay work --install --yes`, then report the lanes the worker now serves. In full:

1. `npx @kyleroche/relay setup --site <site>` — joins the hosted relay: the site URL goes to `~/.harness/config.json`, a scoped token to `~/.harness/credentials.json` (0600). The device flow needs the user's browser; `--invite <code>` skips it. The site holds memory and the feed and shows the board; the tasks themselves are on the board (next step). Without a hosted site skip this step: memory then uses the embedded database under `~/.harness`.
2. `vercel login`, then `npx @kyleroche/relay setup --board`: the tasks live on the team's Vercel Board, and the board takes this machine's own Vercel login (Vercel CLI 66 or newer; `BOARD_TOKEN` in CI, `BOARD_URL` for a local board from `npx vb serve`). There is no relay credential for it and nothing to copy. `vercel login` needs the user's browser: stop for it. `relay setup --board` checks that the login reaches the board, prints who the machine is there and whose tasks it takes, registers relay's schemas (once per team; that takes `manage` on the board, and `relay work` does not start on a board without them, so when the login lacks it, tell the user who must run it once) and saves what was named in the `board` entry of `~/.harness/config.json`: `--team <id>` for a team other than the login's default, `--board-name <name>` for a named board (`--create` makes it when the team does not have it), `--from <actors>` for the owners whose tasks this machine claims besides the user's own (a task's text is instructions for whoever claims it, so add an owner only when the user names it). When a hosted relay exists and the user's login manages the board, add `--site-project <the Vercel project that runs the site>`: it grants that project's production deployment the queues and adds it to `board.from`, so this machine takes the tasks the site opens (from its pages, its API, its MCP tools or a labelled GitHub issue), and it prints the `RELAY_BOARD_FROM` line the user sets on the site's project so the site counts this machine's runs and usage. The user names the project; do not guess it.
3. `npx @kyleroche/relay doctor` — reports which CLIs are installed and logged in (`claude`, `codex` or `fx`, `grok`, `gh`), Node version, the site check, database reachability, a `sandbox` line (Claude Code's OS sandbox, and the sandbox runtime a project's setup and verify commands run under; a warning that the runtime is missing is fixed by reinstalling relay), a `board` line (which board, as whom, how many workers; its failure text is the fix), a `recorded` line (a Node path relay wrote into a hook, MCP or service file that no longer exists, or a service file that passes an option `relay work` does not take; fix: `relay setup --yes`, and `relay work --install --yes` for the service), and a `lanes` line: the lanes `relay work` would serve from these logins. Tell the user what is missing; logins are theirs to do (`gh auth login` and `gh auth setup-git` are needed for every lane, since the worker pushes as the gh account).
4. `npx @kyleroche/relay work --install` — prints the service file (a LaunchAgent on macOS, a systemd user unit on Linux) that keeps `relay work` running, and writes nothing; `--install --yes` writes and starts it (the user's request to make this machine a worker is the consent). `npx @kyleroche/relay work status` shows the service, the board's workers and the log tail; report the lanes this worker serves. `--lanes claude,codex` forces a subset, `relay work --once` drains the queue in the foreground. `docs/WORKERS.md` has the loop, what a job does and the troubleshooting. On a Mac with Apple's `container` CLI installed (`doctor` has a `container` line), prefer the container tier when the user asks for isolation or the Mac is their daily machine: `npx @kyleroche/relay work --isolation container --install --yes` builds the image, creates the `relay-work` container, joins the hosted site from inside when there is one (the device flow's code prints to the terminal; stop for the user's browser; no site is required) and installs the service; then the logins happen inside and are the user's to do, with one command from the Mac: `npx @kyleroche/relay work container login all` (claude, gh and vercel run in the terminal: `/login` with a pasted code, a device code, and a device code for the Vercel login the worker inside reaches the board with; codex and grok open the Mac's browser and relay catches the redirect; logins already in the volume are skipped). The Mac's `~/.harness/config.json` is not mounted: for a board other than the login's default, or owners in `--from`, set `RELAY_BOARD_TEAM`, `RELAY_BOARD_NAME` or `RELAY_BOARD_FROM` in the environment at install time, or run `relay setup --board` inside. Run it in the user's terminal, since it needs their browser and keyboard; stop and tell them when it waits. The by-hand fallback it prints on a failure: `relay work container shell`, then `claude` (`/login`), `gh auth login && gh auth setup-git`, `vercel login`, `fx login codex`, `FX_NO_OPEN_BROWSER=1 fx login grok` (paste only the `code` value from the unreachable callback page). `relay work container status` shows the lanes the container worker serves. Nothing from the Mac's home is mounted into it. After `git pull` or a package upgrade, `npx @kyleroche/relay work container update --yes` rebuilds the image and recreates the container; the volume's site token and logins are kept, so no new device flow.
5. `npx @kyleroche/relay setup` — prints every file it would touch in `~/.claude`, `~/.codex`, `~/.grok` (hooks, the memory MCP server, and Claude Code's `statusLine`: relay's status-line script saves the 5-hour and weekly plan usage Claude Code reports to `~/.harness/meters`, which is where the web app's header meters come from; a status line the user already has is kept and run by relay's; `--no-statusline` skips it) and writes nothing; run `npx @kyleroche/relay setup --yes` when the user asked for relay on this machine; ask first only if they did not. The hooks record the installed package's own files and the Node that ran `setup`. The meters file appears after the user's first interactive `claude` session; `relay doctor` shows it.
6. In each repo they want managed: `cd <repo> && npx @kyleroche/relay link`. Adding a project is this one command and one pull request to merge. It registers the project and hashes its files, digests the changed files and writes the project summary (Sonnet lane, needs the `claude` login; `--no-digest` skips it, `--max-files` caps it at 400 by default), adopts what Claude Code knows about the repo on this machine with no model call (memory notes of type project or reference become files under `docs/context/` with an index, notes of type feedback or user become decisions in relay's memory scoped to the project, and the commands its transcripts ran, counted with their arguments dropped, become a first `.relay/project.json` when the repo has none; a note that looks like it holds a secret is left out whole and named; `--no-adopt` skips all of it, and `relay adopt` prints the plan and writes nothing), and proposes every repository file as one pull request against the default branch on the branch `relay/link`: the owned section of `AGENTS.md`/`CLAUDE.md`, `.relay/rules.json`, `relay.md`, the `docs/context/` notes, the drafted profile, and the removal of caller workflows relay itself wrote. The checkout is not written. Without an `origin` on GitHub or without `gh`, or with `--no-pr`, the same files are written into the working tree instead. It also adds the GitHub labels (`gh`; `--no-labels` skips them), prints every stage and one cost line, and ends with a `left:` line for each thing only the user can do, or `done:`. Give the user the `left:` lines verbatim: the pull request to merge (they should read the adopted notes and the drafted profile in it first; workers read all of these files from the default branch, so nothing takes effect until it is merged) and, in site mode, the install link when its `events` stage finds the site's GitHub App is not installed on the repo (one install covers every repo they pick; `--no-events` skips the check). Do not merge the pull request for them unless they ask. What adoption found is the one thing `relay link` asks about: it lists the notes and preferences and waits for a yes at the terminal, because a yes pushes notes written for one person on one machine to the repository's host and sends the preferences to relay's memory; with no terminal and no `--yes` it leaves them out and names them. As an agent, run `relay adopt` first, show the user what it lists, and pass `--yes` only when they said to include them; otherwise run `relay link --no-adopt`. Re-running is safe: it makes no model calls unless files changed, records each adopted decision once, and while the pull request is open it reads the branch as it stands, a reviewer's commits included, and adds one commit on top with a comment saying what it added (it replaces only a branch left over from a pull request that was merged or closed); `--refresh` rewrites the summary. Do not run `relay project digest` or `relay project summarize` by hand. `.relay/project.json` is the project's profile (`docs/PROFILE.md`): the commands a worker runs before and after the work, the project's tools and skills, and the capability sets a task may be granted. To have that repo's tasks run steps (comment cleanup before the PR, a second lane's eval after it), `relay steps add remove-yap` and `relay steps add eval` list them in `.relay/project.json`; commit it, and it takes effect once it is on the default branch (`docs/STEPS.md`). Ask before adding steps nobody asked for.
7. Optional, for a model the user will prompt (image/video models): `npx @kyleroche/relay onboard <provider/model>`.

If you are an agent that wants to call the hosted site yourself, request access the same way, without a human handing you a token: `POST <site>/oauth/device` (`client_name`, `scope`), show the user the `user_code` to approve at `<site>/activate`, poll `POST <site>/oauth/token` with `grant_type=urn:ietf:params:oauth:grant-type:device_code`, then call `/mcp` or `/api/v1` with the bearer; `docs/INTEGRATIONS.md` has the sequence and the invite and consent alternatives.

From a checkout instead (contributors, or a machine that should track `main`): `git clone <repo> && cd relay && pnpm install`, then `pnpm relay setup --board`, `pnpm relay doctor`, `pnpm relay setup` and `pnpm relay work --install` (through `pnpm`, so the hooks and the service record the pinned Node 24) and `<relay checkout>/bin/relay link` in each repo. Everything else is the same.

### A clean machine, what the first install hits

Lessons from real installs; `relay doctor` prints the fix for each, give it to the user verbatim:

- **Node 24 without Homebrew**: the installer from nodejs.org, or a version manager; `relay` refuses older Node. Check `node -v` before anything.
- **`relay` not found after `npm install -g`**: npm's global bin directory is not on the shell's PATH (a prefix such as `~/.local/node`); `relay doctor`'s `path` line prints the `echo 'export PATH=…' >> ~/.zshrc` line. `npx @kyleroche/relay <command>` works meanwhile.
- **`gh` missing and no Homebrew**: the macOS pkg from https://github.com/cli/cli/releases/latest, then `gh auth login && gh auth setup-git`. No lane can push without it.
- **Codex and Grok lanes** need `fx` (tarball from https://releases.fx.sh) or the vendor CLIs, each logged in; a machine with only the Claude login is a claude-only worker, which is fine.
- **`launchctl bootstrap gui/<uid>` fails with "Input/output error"** when the user has no desktop session (SSH onto a Mac nobody is logged into). relay falls back to the `user/<uid>` domain and says so; for a worker that must survive logouts, log in once on the screen (or enable automatic login) and re-run `relay work --install --yes`.
- **The container tier** (`--isolation container`) needs Apple's `container` tool installed and `container system start`, and its own Vercel login inside for the board (`relay work container login vercel`, part of `login all`); without it, use host mode (`relay work --install --yes`), which still runs the Claude lane in Claude Code's own sandbox.
- **`relay doctor`'s `board` line fails, or `relay work` says it cannot reach the board**: the machine has no Vercel login, an expired one, or one that is not on the team that owns the board. `vercel login` (Vercel CLI 66 or newer), then `relay setup --board`; `--team <id>` when the board belongs to a team other than the login's default.
- **Stop at anything that needs the user's browser or password**: logins (`vercel login` included), the device code on `/activate`, installers.

Never move or copy a login, token, or `auth.json` between machines. Never run with permission checks disabled on a machine that holds the user's logins; `relay work` never passes a bypass flag.
