# AGENTS.md — relay

relay is an open-source harness that lets one person's coding-agent subscriptions (Claude, Codex, Grok) work as one system: the team's Vercel Board is the task bus (a task is a thread in its project's queue, `work/<project>`), workers (machines running `relay work`) on the user's own machines claim tasks from the board with the machine's own `vercel login` and execute them with the vendor CLIs under the machine's own login, pull requests land on GitHub, a Postgres database holds shared memory and an append-only event feed, and a small web app shows it all. No GitHub Actions runner is required. Credentials never leave the machine they were created on.

The CLI, the worker, the web app, its `/api/v1` task routes and the MCP `relay_task_*` tools all read and write tasks on the board through the same functions (`packages/core/src/board/tasks.ts`). The database holds memory, the feed, assets and access; it has no task or worker tables in use.

## Layout

- `packages/core` — TypeScript library: `db/` (Postgres schema + migrations + typed queries for memory, the feed, projects, assets, tokens, OAuth and settings; PGlite locally, Neon in production; the tables of the earlier task model stay in the schema, unused), `board/` (relay on a Vercel Board, exported from `@relay/core` as `board`: `client.ts` the handle, with no relay credential behind it, since `@vercel/board` finds the caller's own (the machine's `vercel login`, `BOARD_TOKEN`, or the board at `BOARD_URL`), and `connectBoard`, which adds who the caller is and the owners it takes tasks from (`from`); `mapping.ts` the vocabulary, pure: the channels `work/<project>` (a project's queue) and `relay/workers`, the labels, which only steer (`lane` and `model` on a task, `relay=<kind>` on relay's own replies), the hold kinds (`awaiting_review` with the pull request's URL as its reason, `gate`, `awaiting_eval`), `relayState` (the board's task state plus the hold's kind as one word: waiting, queued, running, review, held, blocked, done, failed, closed), `branchFor` (`relay/<lane>-<8 hex of the task ID's hash>`) and `isBranchOf`; `schemas.ts` the registered blocks, which carry what relay acts on: `relay-task@1` in a task's own text (repo, base, issue; step, evaluates, branch on a step's task), `relay-run@1` (a run's outcome, branch, pull request, eval task), `relay-eval@1` (an eval's verdict), `relay-release@1` (a gate release, by the digest of the text), `relay-usage@1`, `relay-worker@1`, `relay-asset@1`, with `ensureSchemas`, `isTrustedActor` and `trustedBlocks` (data in a reply counts only from a trusted principal itself or from relay's own `relay-…` profiles of it: a worker's `relay-<worker>-<lane>`, a site's `relay-site` and `relay-brief`; a profile a site writes for a person or a bot never starts that way, so a caller's words are never data) and `prose` (the second layer: a fence in someone else's words that the board would read as a block is posted as a plain one); `tasks.ts` the task commands over the caller's own handle: `openTask` (made out of every worker's reach, pre-checked, then released or held), `openTaskHeldBack`, `getTask` (a thread outside a project's queue is no task; with `trusted`, only relay's own usage rows), `listTasks` (one state or several, oldest first; `open` is everything not done or closed, failed included), `recentTasks` (newest first by latest activity, for the site's Done column and History), `approveTask` (checks that the caller can settle the task before anything merges, merges the pull request the hold names only if its head is a branch relay pushed for the task, or accepts a nodes task's outputs, then completes; a task whose own pull request is already merged is finished from any open state), `requestChanges`, `requeueTask`, `closeTask` (cancels, calls off a step's task that looked at it, sends the work a closed step's task was looking at to review, closes its own open pull requests and deletes their branches), `releaseTask` (a `relay-release@1` block, then the unblock), and `takeHeld`, which takes the `lane` label off before lifting a hold so no worker gets in between; `workers.ts` one message per worker machine in `relay/workers`, its text a `relay-worker@1` block edited in place and its labels `worker`, `status`, `running`, `seen`: `registerWorker`, `listWorkers`, `servedLanes` (the lanes of workers that are online or idle), `forgetWorker` (hides it with a `forgotten` label) and the online / idle / offline / retired thresholds, and `openServedTask`, the open every surface that takes a lane from a person or a bot goes through; `site.ts` what a hosted relay does on the board besides (`docs/ARCHITECTURE.md`, "The site and the board"): `actorProfile` (the site writes for each person or bot as a profile named for them, `human-…` or `bot-…`), `SITE_PROFILE` / `BRIEF_PROFILE` / `INTAKE_PROFILE` (`relay-site` for the site's own data, `relay-brief` for its briefs, `github` for GitHub intake), `syncLedger` / `ledgerRows` (board events become feed rows, from a cursor kept in the settings table; one event the database refuses leaves a `ledger.skipped` row and the rest go on), `postBrief` (a task's `brief.md`), `settleMerged` (a pull request merged on GitHub completes the task that waits on it, in review or still held for an eval) and `grantSite` (the grant `relay setup --board --site-project` makes); `desk.ts` the one layer for what a site does to a task, used by the site's API, its pages and the MCP server: `deskFor` (a caller's words go out as their profile, relay's own data as `relay-site`), `openFor` (the brief is in the thread before a worker can claim the task), `approveFor`, `requestChangesFor`, `releaseFor`, `requeueFor`, `closeFor`, and the two rules for a bot (a token, not a signed-in person): it never approves a task it opened, and it never releases a task whose text it wrote any part of; `local.ts` `memoryBoard`, an in-memory board with relay's schemas for tests and the site's demo mode), `steps/` (`index.ts`: step files with frontmatter, the three layers (relay's, the user's `~/.harness/steps`, the project's `.relay/steps`), the `steps` list of `.relay/project.json`, both read from the repository's default branch during a job; `docs/STEPS.md`), `brief/` (the brief compiler and `relay.md` renderer), `memory/` (transcript capture: parse, gate, extract decisions with the Sonnet lane), `onboard/` (official-vendor-docs ingestion gate), `lanes/` (headless adapters for `claude -p`, `fx`, `codex exec`, `grok -p`; `sandbox.ts` builds the `--settings` document that puts the Claude lane's Bash in Claude Code's OS sandbox on every code run, its denied paths including the Vercel CLI's auth directories and `~/.config/board` since a lane never talks to the board, the tool allowlist in `work/job.ts` being the second layer; `nodes.ts` is the Griptape Nodes lane: it runs `packages/cli/python/run_workflow.py` under the engine's own Python (found through the `griptape-nodes` launcher's shebang, `RELAY_NODES_PYTHON` or `uv tool run`), maps the node types it ran to model ids (`NODE_MODELS`) and turns the outputs into one `step.usage` per output model on lane `video` | `image` | `audio`), `ledger/` (step.usage writer, the token price table and `MEDIA_PRICES` for per-output media models; an unpriced model is recorded with `cost_unknown: true`), `assets/` (Blob or local store, versions, review), `rules/` (owned-section installer for `AGENTS.md`/`CLAUDE.md`), `hooks/` (per-CLI hook installers, including Claude Code's `statusLine`, installers and the brief cache), `meters.ts` (plan-meter readings: the file relay's status line writes under `~/.harness/meters`, what the worker keeps in its message in `relay/workers`, what the site accepts), `state/` (project registration and file digests), `tasks/` (`lanes.ts`: the lane vocabulary every surface shares: `isLaneName` (`[a-z][a-z0-9-]{0,31}`) the shape, `CODE_LANES` (claude, codex, grok), `WORKER_LANES`/`BUILTIN_LANES` the four `relay work` serves, `ANY_LANE` (`any`: whichever code lane is free), `laneUnservedProblem(lane, registered)` the rule that refuses a lane no worker lists; `gate.ts`: the injection gate, a deterministic pre-check when a task is opened plus one Sonnet call with no tools on the worker that grades the task's text before a lane runs it; `manifest.ts`: the nodes lane's ```relay-nodes block, parsed from the task's body (JSON or a small YAML subset, no library) into the workflow path, the flow inputs and the end nodes to keep), `github/` (`client.ts`: pull requests, issues and comments over the GitHub App, `GITHUB_TOKEN` or `gh`; `app.ts`: installation tokens from `GITHUB_APP_ID` + `GITHUB_APP_PRIVATE_KEY` via jose, cached per installation), `oauth/` (the OAuth 2.1 authorization server, framework-free: PKCE codes, refresh rotation, RFC 8628 device codes, RFC 7591 registration, revocation, the `urn:relay:invite` grant; `db/oauth.ts` holds its queries, `db/settings.ts` the sealed settings), `client/` (`RelayClient`: memory, the feed, projects, tokens and invites over the local database or a hosted site, chosen by `openHarness()`; it has no task methods, since tasks are on the board; including `githubStatus(slug)` (`GET /api/v1/projects/{slug}/github` on a site; no App and the site's `/setup/github` as install link locally); `device.ts` is the CLI side of the device flow, invites and refresh), `work/` (the worker on the board: `worker.ts` the loop: it does not start on a board without relay's schemas unless its login can register them; one claim per free lane under `work/` (the worker's own lanes in order, then `any` on a free code lane), only from the owners in `from`, never two jobs on one lane, a blocking wait on the board when there is nothing to take (no timer polling; it looks again every 5 minutes), and the worker's message in `relay/workers` kept current with its lanes, labels, version and plan meters; `job.ts` one claimed task to a PR held for review: the thread read (`runState` reads what earlier runs left in trusted blocks), the claim kept (`keepClaim`: renewed at a third of the lease, a lost claim aborts the lane's CLI, and the board is asked once more right before the push), the clone, the project's steps from the default branch, the injection gate (skipped for text a `relay-release@1` block covers), then one of three: `runCodeTask` (branch `relay/<lane>-<ref>`, the brief (the thread's `brief.md` from a trusted author, else the machine's own memory), the lane with the task's `model` label, the `before-pr` steps, the commit as the machine's gh login with relay-agent as co-author, push, PR, and `openJudge` for an `after-pr` step), `runNodesTask` (one workflow run to `relay-asset@1` attachments in the thread) or `runStepTask` (a step's own task: findings and a `relay-eval@1` block in the work's thread); the result, a `relay-run@1` block and the `relay-usage@1` blocks go in the thread and the task is held; `service.ts` the LaunchAgent/systemd files; `container.ts` and `login.ts` the container tier).
- `packages/cli` — the `relay` command. `src/commands/` holds one file per command group (`setup`, `link`, `brief`, `recall`, `decide`, `prefer`, `capture`, `memory`, `assets`, `token`, `invite`, `task`, `steps`, `work`, `lane`, `project` (`relay project add <slug> [path] --repo owner/name`: a project without a checkout, such as a production, through `RelayClient.registerProject` in either mode; `digest`, `summarize`, `show` stay local); `_board.ts` is the board handle the task and steps commands share; `probes.ts` is the login and sandbox detection `doctor` and `work` share, including `nodesCheck`, the `nodes` doctor line that makes a machine with the Griptape Nodes engine serve the `nodes` lane, `boardCheck`, the `board` line, and `recordedNodeCheck`, the `recorded` line: a Node path relay wrote into a hook, MCP or service file that no longer exists, or a service file that passes an option `relay work` does not take), `python/run_workflow.py` is the Griptape Nodes shim (dependency-free beyond the engine; `--workflow`, `--inputs <json file>`, `--out <dir>`, `--outputs`; one JSON document on stdout), `steps/*.md` are the steps relay ships (`remove-yap`, `eval`, `eval-respond`, `cleanup`; copied to `dist/steps`, `docs/STEPS.md`), `hooks/*.mjs` are the dependency-free scripts the CLIs' hooks point at (`statusline.mjs` is Claude Code's status-line command: it saves the plan meters Claude Code reports to `~/.harness/meters/claude.json`, then runs the status line that was there before), at, `templates/` the Actions caller workflows `relay link --workflows` installs. `relay onboard <model>` ingests vendor guidance; `relay feed`, `relay usage`, `relay doctor`; `relay token create` mints scoped bearer tokens for the web app (hash stored, shown once); `relay task` opens, reads, approves, sends back, requeues, closes and releases tasks on the board, each addressed by the ID the board gave it; `relay steps` (`ls`, `show`, `eject [--user]`, `add`, `rm`, `run`) shows and edits the steps a project runs and opens a task that runs one by itself; `relay setup --board [--team <id>] [--board-name <name> [--create]] [--from <actors>] [--site-project <name>]` saves which board and whose tasks in `~/.harness/config.json`, checks this machine's `vercel login` on it and registers relay's schemas (once per team; `--create` makes a named board the team does not have; `--site-project` grants the Vercel project that runs relay's site everything in `work/` and adds its deployment to `board.from`); `relay work` makes the machine a worker (`--once`, `--install`/`--uninstall` for the LaunchAgent or systemd unit, `work status`, `work forget <name>` hides a retired worker until that machine runs `relay work` again; it waits on the board, so there is no interval to set; `--no-sandbox` turns the Claude lane's OS sandbox off, logged and advertised as the label `sandbox:off`; `--isolation container` runs the whole worker in the `relay-work` container made with Apple's `container` CLI from `container/Dockerfile`, shipped as `dist/container/`: `--install` builds the image (Claude Code, gh, the Vercel CLI, fx, relay), creates the container on a named volume with no host mounts, runs `relay setup --site` inside when a site is known (none is required) and installs a service that runs `container start --attach`; `work container shell|status|stop|start|rm|logs` wrap it; `work container update` rebuilds the image and recreates the container on the same volume, skipping `relay setup --site` when the volume holds a token; `work container login [claude|gh|vercel|codex|grok|all]` makes the logins inside from the Mac (claude, gh and vercel as TTY passthroughs, vercel being the login the worker inside reaches the board with; for codex and grok fx runs inside with `FX_NO_OPEN_BROWSER=1`, its authorize URL is opened in the Mac's browser and the redirect caught by a listener on the Mac at the port fx registered, the code then pasted to fx or, for codex, replayed to its listener inside; the pure parsing is `packages/core/src/work/login.ts`); inside, the worker registers as `<host>-container` with `isolation:container` and `sandbox:on` or `sandbox:container`; `docs/WORKERS.md` "Isolation"); `relay lane settings` prints the sandbox `--settings` JSON for scripts such as `run-lane.sh`; `relay lane nodes --workflow <file> --inputs '<json>'` runs one Griptape Nodes workflow through the nodes adapter by hand (outputs in `--out`, usage rows in the local ledger). `relay setup --site <url>` puts the CLI in site mode through the device flow (it prints a code approved at `<site>/activate`; `--invite <code>` redeems an invite instead, `--token <t>` pastes one): commands and hooks call the hosted site's `/api/v1` and `/mcp` instead of a local database and the token renews itself (`docs/MEMORY.md`, "Site mode"); `relay task`, `relay steps run` and `relay work` use the board in either mode. `relay invite create` mints one-time codes; `relay doctor` shows how the machine authenticates. Published to npm as `@kyleroche/relay`: `tsup.config.ts` bundles `src/main.ts` and the MCP stdio entry with `@relay/core` and `@relay/mcp` into `dist/relay.js` and `dist/relay-mcp.js` (runtime dependencies stay external and are listed in `package.json`, `sharp` optional), and `scripts/postbuild.mjs` copies `hooks/*.mjs`, `python/*.py`, `steps/*.md`, the SQL migrations and `container/` beside them. `runtimePaths()` in `packages/core/src/runtime.ts` tells the hook installers, the migration loader and loader, the template copier, the step loader and the container installer where relay's files are in either layout (checkout or installed package); path code does not count `..` from `import.meta.url` on its own, because the bundle has one `import.meta.url` for every module.
- `packages/mcp` — the relay MCP server `@relay/mcp`: `bin/relay-mcp.mjs` (stdio for the CLIs from a checkout; the published package ships it bundled as `dist/relay-mcp.js`; in site mode it opens no database and `src/bridge.ts` forwards every message to `<site>/mcp` with the machine's token, renewing it on expiry or a 401, so the tools and answers are the site's), `createMcpHandler` (Streamable HTTP for the web app), one tool set for both: public read tools (`relay_get_*`), memory tools (`relay_recall`, `relay_brief`, `relay_guidance`, `relay_feed`, `relay_project`, `relay_decide`, `relay_prefer`), asset tools (`relay_asset_*`), task tools on the board (`relay_task_create`, `relay_task_get`, `relay_task_list`, `relay_task_approve` / `relay_task_request_changes` / `relay_task_requeue` / `relay_task_close` under `tasks:write`, and `relay_task_release` under `tokens:write`: lift the injection gate's hold; every write goes through core's desk (`board/desk.ts`), so over HTTP a bot's words go out as its profile on the site's board handle, it never approves a task it opened and never releases a task whose text it wrote any part of, and over stdio the caller is the machine's own Vercel login, with no such rules), `relay_event_log` (external bots' own `external.*` events, actor always `bot:<token name>`), the public `relay_whoami`, the `tokens:write` access tools (`relay_access_list`, `relay_access_approve`, `relay_invite_create`, `relay_invite_revoke`: a chief-of-staff bot approves other agents' device codes and mints invites, for scopes it holds itself and never `tokens:write`); there are no worker tools and no webhook tools: a worker claims from the board, and a bot that wants to know how a task stands calls `relay_task_get` or `relay_task_list`. Tools are gated by the scopes a token carries (`TOOL_SCOPES` in `src/server.ts`).
- `apps/web` — Next.js app. Tasks and workers come from the team's Vercel Board, not the database (`apps/web/AGENTS.md`, `docs/ARCHITECTURE.md` "The site and the board"): `lib/board.ts` is the one handle (the deployment's own in db mode, an in-memory demo board from `lib/board-demo.ts` in mock mode; `actorBoard` writes as the profile of whoever asked), `lib/board-read.ts` what pages read (`openTasks`, `recentTasks`, `newestFinished`, `fleet`, `planMeters`, `waitingOnYou`), `lib/task-ops.ts` a thin adapter that turns a request from the API routes or the server actions into a call on core's desk (`packages/core/src/board/desk.ts`), where the rules for bots are, `lib/board-watch.ts` with `app/api/board/[[...path]]/route.ts` the two watchers the board wakes the deployment for (`ledger` copies the queues' events into the feed, `brief` posts a new task's brief) and the throttled sync page loads run, `lib/webhooks/board.ts` what a GitHub delivery does on the board (an `agent:<lane>` label opens a task, a merge completes one). Pages: the board (`/` for a signed-in viewer: one column per task state, the approve / request-changes / release / requeue / close actions on the cards, `?project=<slug>` to filter, re-rendered every 20 s; the public landing for an anonymous one), the event feed (`/feed`, the board's second tab), the history (`/history`, the third tab: tasks newest first by latest activity, state and project filters; one project pages back, across projects it is the newest page), task pages (`/tasks/<id>`, the board's ID: the same actions, the thread's notes, usage, and the outputs of a nodes task, listed and not downloadable yet), projects, usage meters, workers, asset library with review (`/assets`), the Access page (`/access`, with `/tokens` redirecting to it: device requests with Approve/Deny, every token and how it was issued, invites, registered clients, the by-hand mint folded away), the OAuth 2.1 authorization server (`/.well-known/oauth-authorization-server`, `/oauth/register|authorize|token|device|revoke`, the consent page, `/activate` for device codes; `lib/oauth.ts` wires `@relay/core`'s server to the site), the GitHub App setup (`/setup/github` with the one-click manifest flow; `lib/github-app.ts` resolves the app from the environment or the sealed settings), info and docs pages, webhook ingest (GitHub org or App deliveries, Vercel), the public read API, the asset API, tasks, external events, tokens, invites, access approvals (`/api/v1/access`), `whoami`, the GitHub status of a project (`/api/v1/projects/{slug}/github`) and project uploads under `/api/v1`, the MCP server at `/mcp`, the retention crons (`/api/cron/assets-expire`, `/api/cron/access-expire`), and the agent-readiness files (`/.well-known/*`, `/openapi.json`, `/llms.txt`). Everything that is not a task or a worker goes through `apps/web/lib/data.ts`: `RELAY_DATA=db` or any `DATABASE_URL` selects `lib/data-db.ts` over `@relay/core` (PGlite when `DATABASE_URL` is unset, one handle per instance in `lib/db.ts`); otherwise `lib/data-mock.ts` serves `lib/mock.ts`. Bearer tokens are checked in `lib/auth.ts` (`tokens` table with expiry, then `RELAY_API_TOKENS`, then `RELAY_MEMORY_TOKEN`); every 401 names the authorization server through `resource_metadata`. `DESIGN.md` there holds the UX brief and tokens.
- `skills/relay/SKILL.md` — the agent skill for installing relay, served at `/.well-known/agent-skills/index.json`.
- `.github/workflows` — reusable runner workflows that repos call with a thin caller: the GitHub Actions path, which still reports through GitHub issues, is tracked by nothing on the board, and is scheduled for removal (`docs/RUNNERS.md`).
- `docs/` — `ARCHITECTURE.md` is the source of truth for design; `AGENT-READINESS.md` is the contract for the hosted site; `VERSIONING.md` is the API deprecation policy; `PRODUCTIONS.md` is how a short runs on relay (one tracker repo, a project per production, the `nodes` lane, assets as the deliverable); `INTEGRATIONS.md` is the connect-in-one-step guide (OAuth with consent, device flow, invite codes, the GitHub App, the task tools and states, Grok Bot walkthrough); `WORKERS.md` is the worker: the board login and `relay setup --board`, the channels, labels and states, the loop, what a job does, review, the nodes lane, isolation, the service; `STEPS.md` is the steps a project runs around a task (the file format, the three layers, the four shipped steps, the eval round, `relay steps`); `SECURITY.md` ("Access for agents") has token lifetimes, rotation and revocation; `HOSTING.md` has the deployment: the team's board and `RELAY_BOARD_FROM`, the environment, the GitHub App setup; `research/` holds dated surveys.

## Commands

```bash
pnpm install          # Node 24+ required (.node-version); bin/relay finds one itself
pnpm -r typecheck
pnpm -r test          # vitest; DB tests run on PGlite, no server needed
pnpm relay --help
pnpm relay setup      # plan hooks + MCP server for the CLIs on this machine (+ Claude Code's plan-meter status line; --no-statusline skips it); --yes writes
pnpm relay setup --board                          # the board this machine works from (after `vercel login`): checks the login, saves which board and whose tasks (--team, --board-name with --create to make one, --from), registers relay's schemas (once per team); --site-project <name> grants the Vercel project that runs relay's site the queues and takes its tasks
pnpm relay link       # in a repo (bin/relay link from elsewhere): digests, summary, relay.md, owned sections, labels, GitHub App check (site mode); --workflows adds the Actions callers; idempotent
pnpm relay brief 42   # the memory envelope a lane would get for issue 42
pnpm relay work --once                            # claim and run ready tasks from the board for the lanes this machine is logged in to, then exit
pnpm relay work --install                         # plan the LaunchAgent / systemd user unit that keeps `relay work` running; --yes writes and starts it
pnpm relay work --isolation container --install   # the container tier (macOS, Apple's `container`): image, relay-work container on a volume, relay setup --site inside when a site is known, service; --yes does it
pnpm relay work container login all               # the logins inside relay-work, from the Mac: claude, gh and vercel (the board) in this terminal, codex and grok through this Mac's browser (or one: login vercel; --force redoes one; --no-open prints the URL)
pnpm relay work container status                  # relay-work running?, the image it runs, relay doctor inside, the lanes it serves (also shell|stop|start|rm|logs)
pnpm relay work container update --yes            # after git pull or a package upgrade: rebuild the image, recreate relay-work on the same volume (site token and logins kept, no new device flow)
pnpm relay work status                            # the service, the board's workers (`retired` after 7 days offline), the log tail
pnpm relay work forget <name>                     # hide a retired worker (renamed or decommissioned machine); its runs stay in their tasks' threads, it shows again if it runs relay work again
pnpm --filter @kyleroche/relay build              # the npm package: packages/cli/dist (relay.js, relay-mcp.js, hooks/, migrations/)
scripts/check-package.sh                          # build, pack, install the tarball into an empty directory, run relay and relay-mcp from there (CI runs it)
pnpm --filter @relay/web dev                      # mock data
RELAY_DATA=db pnpm --filter @relay/web dev        # the CLI's PGlite file (stop the CLI first; PGlite is single-process)
pnpm --filter @relay/web build && pnpm --filter @relay/web typecheck
pnpm relay token create --name ci --scopes feed:read,assets:write   # bearer token for /api/v1 and /mcp, shown once
pnpm relay setup --site https://relay.kyro.house                    # site mode via the device flow: approve the printed code at /activate; --invite <code> or --token <t> instead; --no-site reverts
pnpm relay invite create --for concierge --scopes tasks:read,tasks:write,events:write --expires 24h --uses 1   # one-time code; redeemed with --invite or grant urn:relay:invite
pnpm relay project add nightfall --repo kyleroche/productions                # a project without a checkout (a production): several may share one issues-only repo; idempotent, works in site mode
pnpm relay task create --title "Add dark mode" --lane codex --model <id>      # open a task in the project's queue on the board and print its ID (the board's message ID; --needs <ids>, --base, --repo, --key); relay task get <id>, relay task ls --state review|held, relay task release <id> (lift the injection gate's hold for the text as it stands; RELAY_GATE=off on a worker skips its model call)
pnpm relay task create --title "Cutscene 3" --lane nodes --body-file shot.md  # a production task (--manifest shot.yaml appends the relay-nodes fence for you): the body's ```relay-nodes block names the workflow .py in the repo and its inputs; a worker with Griptape Nodes runs it and attaches the outputs to the task's thread, held for review (docs/WORKERS.md, "The nodes lane")
pnpm relay lane nodes --workflow workflows/cutscene.py --inputs '{"Start Flow": {"prompt": "..."}}' --out out/   # the same engine run by hand, outputs in out/, usage rows in the local ledger
pnpm relay task approve <id>                                                  # squash-merge the PR of a task in review (only a PR from the branch relay pushed for it), or accept a nodes task's outputs, then complete the task; relay task changes <id> --note "…" sends it back to the queue
pnpm relay task close <id> --reason "…"                                       # finish a task without a merge: canceled on the board, its open PR closed and that branch deleted, its issue closed on GitHub; relay task requeue <id> [--lane <lane>] [--model <id>] puts a failed or held one back in the queue
pnpm relay steps ls                                                           # the steps this repo runs around a task (.relay/project.json) and every step it could; relay steps add|rm|show|eject <name> (docs/STEPS.md)
pnpm relay steps run cleanup                                                  # open a task that runs a task step by itself, to its own PR; --scope <path>, --lane, --model
RELAY_PUBLIC_URL=https://relay.kyro.house pnpm --filter @relay/web check:agentic   # is-agentic score gate, after deploy
```

Memory commands (`docs/MEMORY.md`): `relay brief`, `relay recall`, `relay decide`, `relay prefer`, `relay capture`, `relay memory history`. `relay setup` records the hooks and the MCP server as absolute paths: the installed package's `dist/` files when it ran from `npx @kyleroche/relay`, the checkout's `packages/cli/hooks` scripts (which call the CLI through the repo's own `tsx`) when it ran from a clone, so a clone must stay where `relay setup` ran (re-run it after moving).

## Conventions

- TypeScript strict, ESM, `.ts` imports with extensions. No default exports except Next.js pages/routes.
- Plain SQL migrations in `packages/core/src/db/migrations/NNN_*.sql`; never edit a shipped migration.
- Every model call goes through a lane adapter and writes a `step.usage` event. Nothing calls a model directly.
- Official vendor sources only for model guidance (`onboard/registry.ts` allowlists domains). Do not add community prompt guides.
- Secrets live in environment variables, never in files or examples. `.env.example` lists names only.
- Keep `AGENTS.md`, `llms.txt`, and `README.md` accurate when you change commands or layout; CI checks that README commands exist.
- Commit messages: imperative, one topic each. Do not commit generated output, databases, or anything under `.harness/`.

## Installing relay for a user (agent instructions)

If a user asks you to set up relay, do these steps and stop at anything that needs their browser. Their request is the consent for the writes below: when they asked you to set relay up on this machine, make it a worker, or link a repo, run the `--yes` forms without asking again; print the plan and ask only when nobody asked for that step.

relay is on npm as `@kyleroche/relay`; `npx @kyleroche/relay <command>` runs it with no checkout, and `npm install -g @kyleroche/relay` installs the `relay` command (if the shell then cannot find it, npm's global bin directory is not on PATH; `relay doctor`'s `path` line prints the exact fix). It needs Node 24 or newer: check `node -v` first and have the user install 24 (their version manager, or `brew install node@24`) if it is older.

When the user says "set up relay from `<site>` on this machine" (a hosted relay exists), the sequence is: `npx @kyleroche/relay setup --site <site>` (device flow in the user's browser, or `--invite <code>`), `vercel login` (the user's browser) and `npx @kyleroche/relay setup --board`, `npx @kyleroche/relay doctor`, `npx @kyleroche/relay work --install --yes`, then report the lanes the worker now serves. In full:

1. `npx @kyleroche/relay setup --site <site>` — joins the hosted relay: the site URL goes to `~/.harness/config.json`, a scoped token to `~/.harness/credentials.json` (0600). The device flow needs the user's browser; `--invite <code>` skips it. The site holds memory and the feed and shows the board; the tasks themselves are on the board (next step). Without a hosted site skip this step: memory then uses the embedded database under `~/.harness`.
2. `vercel login`, then `npx @kyleroche/relay setup --board`: the tasks live on the team's Vercel Board, and the board takes this machine's own Vercel login (Vercel CLI 66 or newer; `BOARD_TOKEN` in CI, `BOARD_URL` for a local board from `npx vb serve`). There is no relay credential for it and nothing to copy. `vercel login` needs the user's browser: stop for it. `relay setup --board` checks that the login reaches the board, prints who the machine is there and whose tasks it takes, registers relay's schemas (once per team; that takes `manage` on the board, and `relay work` does not start on a board without them, so when the login lacks it, tell the user who must run it once) and saves what was named in the `board` entry of `~/.harness/config.json`: `--team <id>` for a team other than the login's default, `--board-name <name>` for a named board (`--create` makes it when the team does not have it), `--from <actors>` for the owners whose tasks this machine claims besides the user's own (a task's text is instructions for whoever claims it, so add an owner only when the user names it). When a hosted relay exists and the user's login manages the board, add `--site-project <the Vercel project that runs the site>`: it grants that project's production deployment the queues and adds it to `board.from`, so this machine takes the tasks the site opens (from its pages, its API, its MCP tools or a labelled GitHub issue), and it prints the `RELAY_BOARD_FROM` line the user sets on the site's project so the site counts this machine's runs and usage. The user names the project; do not guess it.
3. `npx @kyleroche/relay doctor` — reports which CLIs are installed and logged in (`claude`, `codex` or `fx`, `grok`, `gh`), Node version, the site check, database reachability, a `board` line (which board, as whom, how many workers; its failure text is the fix), a `recorded` line (a Node path relay wrote into a hook, MCP or service file that no longer exists, or a service file that passes an option `relay work` does not take; fix: `relay setup --yes`, and `relay work --install --yes` for the service), and a `lanes` line: the lanes `relay work` would serve from these logins. Tell the user what is missing; logins are theirs to do (`gh auth login` and `gh auth setup-git` are needed for every lane, since the worker pushes as the gh account).
4. `npx @kyleroche/relay work --install` — prints the service file (a LaunchAgent on macOS, a systemd user unit on Linux) that keeps `relay work` running, and writes nothing; `--install --yes` writes and starts it (the user's request to make this machine a worker is the consent). `npx @kyleroche/relay work status` shows the service, the board's workers and the log tail; report the lanes this worker serves. `--lanes claude,codex` forces a subset, `relay work --once` drains the queue in the foreground. `docs/WORKERS.md` has the loop, what a job does and the troubleshooting. On a Mac with Apple's `container` CLI installed (`doctor` has a `container` line), prefer the container tier when the user asks for isolation or the Mac is their daily machine: `npx @kyleroche/relay work --isolation container --install --yes` builds the image, creates the `relay-work` container, joins the hosted site from inside when there is one (the device flow's code prints to the terminal; stop for the user's browser; no site is required) and installs the service; then the logins happen inside and are the user's to do, with one command from the Mac: `npx @kyleroche/relay work container login all` (claude, gh and vercel run in the terminal: `/login` with a pasted code, a device code, and a device code for the Vercel login the worker inside reaches the board with; codex and grok open the Mac's browser and relay catches the redirect; logins already in the volume are skipped). The Mac's `~/.harness/config.json` is not mounted: for a board other than the login's default, or owners in `--from`, set `RELAY_BOARD_TEAM`, `RELAY_BOARD_NAME` or `RELAY_BOARD_FROM` in the environment at install time, or run `relay setup --board` inside. Run it in the user's terminal, since it needs their browser and keyboard; stop and tell them when it waits. The by-hand fallback it prints on a failure: `relay work container shell`, then `claude` (`/login`), `gh auth login && gh auth setup-git`, `vercel login`, `fx login codex`, `FX_NO_OPEN_BROWSER=1 fx login grok` (paste only the `code` value from the unreachable callback page). `relay work container status` shows the lanes the container worker serves. Nothing from the Mac's home is mounted into it. After `git pull` or a package upgrade, `npx @kyleroche/relay work container update --yes` rebuilds the image and recreates the container; the volume's site token and logins are kept, so no new device flow.
5. `npx @kyleroche/relay setup` — prints every file it would touch in `~/.claude`, `~/.codex`, `~/.grok` (hooks, the memory MCP server, and Claude Code's `statusLine`: relay's status-line script saves the 5-hour and weekly plan usage Claude Code reports to `~/.harness/meters`, which is where the web app's header meters come from; a status line the user already has is kept and run by relay's; `--no-statusline` skips it) and writes nothing; run `npx @kyleroche/relay setup --yes` when the user asked for relay on this machine; ask first only if they did not. The hooks record the installed package's own files and the Node that ran `setup`. The meters file appears after the user's first interactive `claude` session; `relay doctor` shows it.
6. In each repo they want managed: `cd <repo> && npx @kyleroche/relay link`. This is the only per-repo step and runs the whole pipeline: registers the project and hashes its files, digests the changed files and writes the project summary (Sonnet lane, needs the `claude` login; `--no-digest` skips it, `--max-files` caps it at 400 by default), writes `relay.md` from that summary, adds the owned section to `AGENTS.md`/`CLAUDE.md`, the GitHub labels (`gh`), and the optional caller workflows (`--no-workflows` skips them; a worker needs none). It prints every stage and ends with one cost line. In site mode its last stage, `events`, checks that the site's GitHub App is installed on the repo and prints the install link when it is not; give that link to the user (one install covers every repo they pick). `--no-events` skips it. Re-running is safe and makes no model calls unless files changed; `--refresh` rewrites the summary. Do not run `relay project digest` or `relay project summarize` by hand. To have that repo's tasks run steps (comment cleanup before the PR, a second lane's eval after it), `relay steps add remove-yap` and `relay steps add eval` list them in `.relay/project.json`; commit it, and it takes effect once it is on the default branch (`docs/STEPS.md`). Ask before adding steps nobody asked for.
7. Optional, for a model the user will prompt (image/video models): `npx @kyleroche/relay onboard <provider/model>`.
8. Not for new installs: `docs/RUNNERS.md` covers self-hosted GitHub Actions runners. That path still reports through GitHub issues, nothing tracks its runs, and it is scheduled for removal.

If you are an agent that wants to call the hosted site yourself, request access the same way, without a human handing you a token: `POST <site>/oauth/device` (`client_name`, `scope`), show the user the `user_code` to approve at `<site>/activate`, poll `POST <site>/oauth/token` with `grant_type=urn:ietf:params:oauth:grant-type:device_code`, then call `/mcp` or `/api/v1` with the bearer; `docs/INTEGRATIONS.md` has the sequence and the invite and consent alternatives.

From a checkout instead (contributors, or a machine that should track `main`): `git clone <repo> && cd relay && pnpm install`, then `pnpm relay setup --board`, `pnpm relay doctor`, `pnpm relay setup` and `pnpm relay work --install` (through `pnpm`, so the hooks and the service record the pinned Node 24) and `<relay checkout>/bin/relay link` in each repo. Everything else is the same.

### A clean machine, what the first install hits

Lessons from real installs; `relay doctor` prints the fix for each, give it to the user verbatim:

- **Node 24 without Homebrew**: the installer from nodejs.org, or a version manager; `relay` refuses older Node. Check `node -v` before anything.
- **`relay` not found after `npm install -g`**: npm's global bin directory is not on the shell's PATH (a prefix such as `~/.local/node`); `relay doctor`'s `path` line prints the `echo 'export PATH=…' >> ~/.zshrc` line. `npx @kyleroche/relay <command>` works meanwhile.
- **`gh` missing and no Homebrew**: the macOS pkg from https://github.com/cli/cli/releases/latest, then `gh auth login && gh auth setup-git`. No lane can push without it.
- **Codex and Grok lanes** need `fx` (tarball from https://releases.fx.sh) or the vendor CLIs, each logged in; a machine with only the Claude login is a claude-only worker, which is fine.
- **`launchctl bootstrap gui/<uid>` fails with "Input/output error"** when the user has no desktop session (SSH onto a Mac nobody is logged into). relay falls back to the `user/<uid>` domain and says so; for a worker that must survive logouts, log in once on the screen (or enable automatic login) and re-run `relay work --install --yes`.
- **The container tier** (`--isolation container`) needs Apple's `container` tool installed and `container system start`, and its own Vercel login inside for the board (`relay work container login vercel`, part of `login all`); without it, use host mode (`relay work --install --yes`), which still runs the Claude lane in Claude Code's own sandbox.
- **`relay doctor`'s `board` line fails, or `relay work` says it cannot reach the board**: the machine has no Vercel login, an expired one, or one that is not on the team that owns the board. `vercel login` (Vercel CLI 66 or newer), then `relay setup --board`; `--team <id>` when the board belongs to a team other than the login's default.
- **Stop at anything that needs the user's browser or password**: logins (`vercel login` included), the device code on `/activate`, installers.

Never move or copy a login, token, or `auth.json` between machines. Never run with permission checks disabled on a machine that holds the user's logins; `relay work` never passes a bypass flag.
